## 2. Architecture decisions carried forward

### DEC-0.6-01 — Keep hybrid architecture

**Decision:** retain the context frame, eight responsibility layers, typed relationship graph, cross-cutting overlays, and viewpoints as the current candidate.

**Reason:** the structure is expressive across a small standalone application, ANANTA, and FireBot without requiring one-to-one component/layer mapping.

**Status:** provisional pending independent review.

### DEC-0.6-02 — Allocate responsibilities, not whole components

**Decision:** use the `realizes(element, responsibility)` relation and a single primary layer per core responsibility.

**Reason:** ANANTA crates and FireBot subsystems may span multiple responsibilities. Whole-component single-layer allocation would be misleading.

**Status:** retain in formalization draft.

### DEC-0.6-03 — Keep evidence status first-class

**Decision:** planned, documented, simulated, repository-reported implemented, executed, tested, observed, and verified must remain distinct.

**Reason:** FireBot simulation, interface contracts, and proposed integration must not be confused with hardware or live network implementation.

**Status:** retain and harmonize terminology.

### DEC-0.6-04 — Preserve technology specification independence

**Decision:** DUSRM must map ANANTA, CONTRACT, CALLGRAPH, OCTET, DATAGRAM, Relay, and other technologies to system responsibilities without redefining their APIs, protocols, data formats, engines, or runtime semantics.

**Reason:** DUSRM is a reference model, not a replacement specification for the existing technologies.

**Status:** core design principle.

## 3. Candidate decisions not yet accepted

- Renaming or reordering the eight layers.
- Adding a ninth layer.
- Making the responsibility graph machine normative.
- Defining a canonical DUSRM file format.
- Building a DUSRM validator or compiler.
- Declaring any system formally conformant.

These require evidence and review rather than intuition.
