# DUSRM 0.6 — Reproducibility Checklist

**Status:** Working validation checklist; non-normative

## Before assessment

- [ ] Record DUSRM draft, document revisions, and applicable profile.
- [ ] Identify SOI, purpose, scope, boundary, environment, and exclusions.
- [ ] Record exact repository names, branches, and source files.
- [ ] Capture blob/commit identifiers for key evidence.
- [ ] Distinguish public and private project material.
- [ ] State what was inspected and what was actually executed.

## Structural mapping

- [ ] Map responsibilities before assigning elements.
- [ ] Assign exactly one primary layer per core responsibility.
- [ ] Allow each element to realize multiple responsibilities.
- [ ] Mark external elements and dependencies explicitly.
- [ ] Type every relationship and declare its scope.
- [ ] Identify cross-layer and feedback relations.
- [ ] Map cross-cutting concerns to affected elements and relationships.
- [ ] Record unmapped or ambiguous responsibilities as gaps.

## Operational mapping

- [ ] Separate operation definitions from execution occurrences.
- [ ] Define state ownership and state meaning.
- [ ] Record transitions, guards, effects, and failure conditions.
- [ ] Distinguish occurrence time, observation time, and processing time.
- [ ] State concurrency, synchronization, and causal-order assumptions.
- [ ] Describe failure, degradation, interruption, and recovery.
- [ ] Separate safety properties from progress/liveness claims.

## Evidence integrity

- [ ] Label every material assertion.
- [ ] Do not call simulated data measured.
- [ ] Do not call planned contracts implemented integration.
- [ ] Do not call repository-reported code executed or tested.
- [ ] Do not call a test verified without a criterion and evidence.
- [ ] Preserve uncertainty and unknown values.
- [ ] Link evidence to the exact claim it supports.

## FireBot-specific checks

- [ ] Keep emergency-stop and safety-critical local control independent of network/database/AI availability.
- [ ] Keep simulation status visible.
- [ ] Do not infer physical effect from a command or acknowledgment alone.
- [ ] Validate authority precedence and degraded mode behavior.
- [ ] Separate future hardware and live fleet capabilities from current simulation.

## ANANTA-specific checks

- [ ] Preserve the documented single-writer and transaction boundaries.
- [ ] Do not imply MVCC, multi-writer, general ACID, or replication guarantees without evidence.
- [ ] Distinguish AQL/query semantics, execution, data state, and storage realization.
- [ ] Preserve native file format and WAL specifications as independent technical contracts.
- [ ] Distinguish optional FireBot JSONL workload from live database integration.

## Final report

- [ ] Report pass, pass-with-findings, fail, or not-assessable per check.
- [ ] State scope, exclusions, assumptions, and tool versions.
- [ ] Record results, evidence, and limitations.
- [ ] Add unresolved findings to the DUSRM gap register.
- [ ] Do not present a DUSRM assessment as a safety certification or system acceptance.
