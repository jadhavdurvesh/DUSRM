# DUSRM 0.6 — Validation Method

**Document ID:** DUSRM-VAL-001  
**Status:** Working draft; non-normative  
**Version:** 0.6-draft

## 1. Purpose

This method evaluates whether a DUSRM system description is understandable, internally consistent, traceable, and useful across different engineering domains.

It assesses the **description and its supporting evidence**. It does not automatically assess the quality, correctness, safety, or fitness of the real system.

## 2. Validation units

A validation exercise should identify three distinct subjects:

1. **DUSRM core:** the ontology, responsibility layers, relationship semantics, operational semantics, and applicable formal rules.
2. **System of interest (SOI):** the actual, planned, or hypothetical system being described.
3. **DUSRM system description:** the representation, mapping, assumptions, evidence, and profile used for the exercise.

Where implementation evidence is available, it must be linked to the relevant assertion. A model diagram alone is not implementation evidence.

## 3. Required evidence labels

Use the following labels on assertions and mappings:

| Label | Meaning | Minimum evidence |
|---|---|---|
| Documented | A project source describes the property or behavior | Exact document and version |
| Repository-reported implemented | Repository documentation says code/functionality exists | Source path or specification; execution still not independently checked here |
| Executed | A named command, test, or procedure was actually run | Command, environment, result, timestamp |
| Observed | Behavior was observed in a specified environment | Observation record and context |
| Tested | A requirement was exercised using a defined test | Test identifier, steps, output |
| Verified | A claim was assessed against a declared criterion using adequate evidence or proof | Criterion, method, evidence, reviewer |
| Simulated | Behavior is generated by a simulation or test fixture | Scenario and simulation source |
| Planned | Intended design or future capability | Plan/contract/roadmap source |
| Assumed | Temporarily accepted without sufficient evidence | Assumption, rationale, impact |
| Unknown | Available sources do not establish the claim | Explicit gap record |
| Not applicable | Claim is outside the declared system boundary | Scope rationale |

These labels are not interchangeable. For example, repository-reported implemented is not executed, and simulated is not physical implementation.

## 4. Validation procedure

### Step 1 — Declare the SOI

Record:
- system identity and purpose;
- system boundary and exclusions;
- environment and external participants;
- abstraction level;
- lifecycle or maturity status;
- description version and DUSRM profile.

### Step 2 — Establish evidence baseline

Record exact source repositories, branches, documents, and revisions. Distinguish public and private source material. Do not copy private source contents into the public DUSRM repository without explicit authorization; this repository may contain source references and short factual summaries only.

### Step 3 — Map responsibilities to layers

- Define responsibility statements before allocating elements.
- Assign each core responsibility one primary layer.
- Map elements to responsibilities through the many-to-many `realizes` relation.
- Leave unknown or unmapped concerns explicit.
- Never force a component into one exclusive layer.

### Step 4 — Map structure and relationships

Record:
- membership and decomposition;
- dependencies and interfaces;
- information, resource, control, and authority relations;
- cross-layer relationships;
- external interactions;
- cross-cutting concerns.

Every relationship must have a declared type, scope, status, and rationale.

### Step 5 — Map behavior

Where applicable, document:
- operation specifications;
- execution occurrences;
- states and state owners;
- events and time meanings;
- transition guards and effects;
- concurrency and causal assumptions;
- failure, degraded operation, and recovery;
- safety and progress claims.

### Step 6 — Trace requirements and evidence

Connect relevant needs, requirements, responsibilities, elements, operations, transitions, verification criteria, and evidence. A traceability link does not itself prove satisfaction.

### Step 7 — Evaluate consistency

Use the checks in the 0.5 formalization documents and the DUSRM 0.6 checklist. Record pass, pass-with-findings, fail, or not-assessable for each check.

### Step 8 — Record model gaps

If a real system responsibility cannot be expressed without distortion:
- record the missing concept;
- show the concrete example;
- explain why existing concepts are inadequate;
- propose a change separately;
- assess impact on existing profiles and earlier descriptions.

Do not change the core model solely to accommodate an implementation quirk.

## 5. Structural checks

| ID | Check | Passing condition |
|---|---|---|
| VAL-S01 | Scope | SOI, boundary, purpose, exclusions, and abstraction level are explicit |
| VAL-S02 | Responsibility definition | Every allocated responsibility has a distinct definition and rationale |
| VAL-S03 | Primary layer | Every core responsibility has exactly one primary layer |
| VAL-S04 | Many-to-many realization | Elements can realize multiple responsibilities without forced splitting |
| VAL-S05 | Relationship typing | Relationship types and participant roles are defined |
| VAL-S06 | Cross-layer traceability | Non-adjacent dependencies and feedback are explicit |
| VAL-S07 | Cross-cutting concerns | Scope and affected elements/relations are named |
| VAL-S08 | Applicability | Applicable, not-applicable, unknown, and not-modeled statuses are distinct |

## 6. Operational checks

| ID | Check | Passing condition |
|---|---|---|
| VAL-O01 | Operation/execution | Specifications and individual execution occurrences are distinct |
| VAL-O02 | State ownership | Every state variable has a declared owner and meaning |
| VAL-O03 | Transition completeness | Source, trigger/guard, effect, destination, and assumptions are identified where applicable |
| VAL-O04 | Event time | Occurrence, observation, processing, and recording times are not conflated |
| VAL-O05 | Concurrency | Ordering and synchronization assumptions are explicit |
| VAL-O06 | Failure semantics | Fault, error, failure, degraded mode, and recovery are distinguished |
| VAL-O07 | Safety/progress | Safety and liveness claims state scope and assumptions |
| VAL-O08 | Evidence status | Planned, simulated, implemented, tested, observed, and verified claims remain distinct |

## 7. Technology-boundary checks

| ID | Check | Passing condition |
|---|---|---|
| VAL-T01 | Technology neutrality | DUSRM describes responsibilities without mandating a product or language |
| VAL-T02 | No duplication | Existing APIs, protocols, encodings, engines, and safety mechanisms retain their own specifications |
| VAL-T03 | Mapping evidence | Technology-to-layer mappings are source-backed and status-labelled |
| VAL-T04 | Integration maturity | Proposed integration is not represented as a working integration |
| VAL-T05 | Domain profile consistency | Profile extensions map to core concepts or are explicitly declared as extensions |

## 8. Result categories

- **Pass:** all applicable required checks pass with adequate evidence.
- **Pass with findings:** required checks pass, but limitations, assumptions, or non-blocking gaps remain.
- **Fail:** one or more required checks fail.
- **Not assessable:** essential scope, source, or evidence is missing.

The result applies to the system description at a specified DUSRM version and profile. It does not certify a real system.

## 9. Reproducibility

A validation record must include:
- DUSRM version and document revision;
- SOI and profile version;
- source repositories, branches, and file revisions;
- test commands or assessment steps actually run;
- environment and tools;
- results and evidence;
- reviewer and date;
- exclusions and known limitations.

Never claim that tests ran when only test plans or repository documentation were inspected.
