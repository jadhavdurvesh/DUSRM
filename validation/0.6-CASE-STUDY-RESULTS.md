# DUSRM 0.6 — Case-Study Results

**Document ID:** DUSRM-VAL-003  
**Status:** Preliminary validation report; non-normative  
**Date:** 2026-11-09

## 1. Summary

Three case studies were mapped against the DUSRM 0.3–0.5 drafts:
- a small standalone software application;
- ANANTA as a native database/data engine;
- FireBot as a software-first cyber-physical robot concept.

The exercise shows that the current hybrid model can describe these three different scopes at a high conceptual level. It also exposes several ambiguities that need further work.

This is a **documentation and model-coverage exercise**, not an independent system verification, formal proof, conformance certification, or safety assessment.

## 2. Results by case study

| Case study | Coverage observation | Main result | Evidence maturity |
|---|---|---|---|
| Standalone application | All eight layers can be interpreted, with infrastructure external and networking not required | Model can scale down without requiring distributed or hardware-specific subsystems | Illustrative only |
| ANANTA | All eight responsibilities can be mapped to documented engine/platform responsibilities | Responsibility-based mapping accommodates a database engine without redefining AQL, ANF, WAL, or API contracts | Repository-documented; execution not independently run here |
| FireBot | All eight responsibilities can be mapped, while physical and live-network layers remain planned | Model captures cyber-physical intent and prevents simulation from being confused with implementation | Repository-documented; several capabilities planned/simulated |

## 3. Standalone application findings

The task-list application example demonstrates:
- L8 can describe user outcomes;
- L7 can describe application capabilities;
- L6 can describe UI and internal interaction without a network;
- L4 and L5 can distinguish application state from task operations and derived calculations;
- L1 and L2 can describe host infrastructure and resource context without requiring the application to own them.

**Finding:** DUSRM must allow a layer's responsibility to be external, optional, or not applicable relative to the selected SOI. A software application does not need to implement eight software modules.

## 4. ANANTA findings

Repository documentation supports mapping:
- L1 to host hardware/filesystem primitives;
- L2 to bounded API/execution resource constraints and single-writer ownership;
- L3 to execution operators, cancellation, iterator lifecycle, and operation-scoped commit/recovery;
- L4 to values, schemas, catalog, native artifacts, and persisted state;
- L5 to AQL parsing/planning/optimization and computational/analytical operators;
- L6 to embedded API and AQL client interaction;
- L7 to database capabilities;
- L8 to the native data-platform purpose and workloads.

**Finding A-01:** L3, L4 and L5 are distinguishable for ANANTA when execution behavior, persisted state, and query/computation semantics are separately described.

**Finding A-02:** A storage artifact may be relevant to L4 as information/state and L1/L2 as a physical file/resource realization. The model must express multiple responsibilities without assigning the artifact itself to one exclusive layer.

**Finding A-03:** ANANTA's transaction guarantees are scoped: operation-scoped atomic redo units, one exclusive writer, shared-reference readers on the same handle, no MVCC, and no general multi-operation ACID semantics. DUSRM must preserve these exact boundaries rather than using the broad phrase "transactional database" as a substitute.

**Finding A-04:** The documented FireBot workload connector is file-based JSONL. It establishes an optional workload path, not a live FireBot integration.

## 5. FireBot findings

Repository documentation supports mapping:
- L1 to intended physical robot hardware and environment;
- L2 to simulated power allocation and planned resource budgets;
- L3 to simulation actions and planned firmware/local control;
- L4 to state and subsystem message contracts;
- L5 to simulation route planning and future perception/mapping computations;
- L6 to proposed interfaces, subsystem coordination, and planned network integration;
- L7 to dashboard and simulated capabilities;
- L8 to people-first rescue/firefighting goals.

**Finding F-01:** FireBot requires explicit maturity labels at every layer. A simulated feature must remain simulated; a contract must remain a contract; a planned hardware function must remain planned.

**Finding F-02:** Safety and authority are cross-cutting. They cannot be assigned to one layer and treated as solved.

**Finding F-03:** DUSRM must distinguish a command, an acknowledgment, and a verified physical effect. A command sent to a controller is not proof of movement or actuation.

**Finding F-04:** ANANTA is a separate database project. The inspected workload documentation shows a file-based FireBot event connector; it does not demonstrate a live network database dependency.

## 6. Cross-case findings

| Finding | Observation | Proposed response |
|---|---|---|
| X-01 | Elements may realize responsibilities across several layers | Keep responsibility-based allocation as a core rule |
| X-02 | The same layer can be external to an SOI or only indirectly represented | Require explicit boundary and allocation status |
| X-03 | Layer order is not execution order | Keep the relationship graph and operational transition model separate |
| X-04 | Simulation and implementation are often mixed in project documentation | Require evidence labels and provenance |
| X-05 | Cross-cutting safety, trust, time, and lifecycle cannot be represented as one isolated layer | Preserve overlays and explicit affected elements |
| X-06 | A system integration plan does not prove integration | Require source/runtime/test evidence before marking integrated |

## 7. Validation outcome

The candidate structure **passes a preliminary descriptive coverage exercise with findings** across the three examples. This is not a formal conformance result because:
- standalone app case is illustrative;
- ANANTA code/tests were not executed as part of this DUSRM exercise;
- FireBot physical hardware and several live subsystems are not implemented according to its repository status;
- the layer definitions and formal rules remain drafts.
